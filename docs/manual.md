# ZeleBoba Billing · Руководство оператора

Полное руководство по развёртыванию, настройке и эксплуатации ZeleBoba Billing — PHP-биллинга подписок для Remnawave с веб-кабинетом, Telegram-ботом, кошельком, 26 платёжными провайдерами, промокодами, реферальной программой, подарками, триалами, маркетингом и админкой.

**Продукт остаётся ZeleBoba.** Название, логотип, цвета и тексты бота настраиваются через админку — код менять не нужно. **Реальный приём денег включается только после проверки конкретного магазина, панели и публичного HTTPS-домена.**

---

## 1. Что это и как устроено

ZeleBoba — модульный монолит на PHP 8.4+, Symfony 7.4 LTS (HttpFoundation, Routing, HttpClient, Console), Twig, PDO и PostgreSQL 17. SQLite допустима только для локальной разработки.

```
Web-кабинет / админка ──► PHP: Web / Identity / Billing
Telegram webhook ──────► PHP
Провайдеры webhook ────► Проверка через API провайдера ──► PHP
PHP ──► PostgreSQL (заказы / квитанции / учёт / outbox / кошелёк)
PostgreSQL ──► Worker ──► Провайдеры / Remnawave / Telegram Bot API
Scheduler ──► Плановая сверка платежей и синхронизация
```

Ключевые принципы:

- **Только целые копейки** (BIGINT), валюта RUB. Суммы от провайдеров разбираются без float.
- **Snapshots**: цена, срок, устройства и трафик копируются из тарифа в заказ. Изменение тарифа не меняет существующий заказ.
- **Идемпотентность**: ключ заказа уникален внутри пользователя; платёж уникален по provider/payment_id; повторное уведомление не создаёт вторую подписку.
- **Durable outbox**: внешний API не вызывается внутри транзакции оплаты. Падение панели не теряет оплаченный заказ.
- **At least once**: повтор уведомления возможен, но денежные операции не дублируются.
- **Секреты зашифрованы** (XChaCha20-Poly1305), ключ в `var/master.key`, payload outbox тоже шифруется.

## 2. Быстрый старт

### 2.1. Требования

- Docker Engine и Docker Compose (для сервера)
- Публичный HTTPS-домен (для боевого режима)
- Панель Remnawave 3.0.0+ с API-ключом
- Telegram-бот от @BotFather
- Один или несколько платёжных провайдеров

### 2.2. Установка

```sh
git clone <ваш-репозиторий> zeleboba
cd zeleboba
cp .env.example .env
```

В `.env` задайте **разные** сильные пароли:

```env
DATABASE_PASSWORD=сильный-пароль-приложения
DATABASE_MIGRATION_PASSWORD=другой-сильный-пароль-мигратора
```

Остальные настройки (Telegram, Remnawave, провайдеры, брендинг) — в веб-админке.

```sh
docker compose build
docker compose up -d db
docker compose run --rm migrate
docker compose run --rm app php bin/console app:install owner@example.com
docker compose up -d app worker scheduler web
```

`app:install` спрашивает пароль скрытым вводом. Встроенных учётных данных нет. Команда требует применённые миграции и отказывается работать при существующем администраторе.

### 2.3. Первичная настройка

1. Настройте HTTPS-прокси по `infra/reverse-proxy.example.conf`. Не открывайте порт 8080 в интернет.
2. Откройте `/login`, войдите владельцем, включите 2FA и сохраните резервные коды.
3. Перейдите в `/admin/config`:
   - укажите публичный HTTPS URL (`APP_URL`), название сервиса, поддержку;
   - настройте Telegram (username, токен, секрет webhook);
   - настройте Remnawave (URL, ключ, группа по умолчанию);
   - настройте провайдеров (см. раздел 5);
   - настройте брендинг (см. раздел 4);
   - оставьте продажи выключенными.
4. Нажмите «Сохранить настройки», затем «Проверить Telegram» и «Зарегистрировать Telegram».
5. Зарегистрируйте webhook'и провайдеров (см. раздел 5.3).
6. Проверьте тестовый сквозной платёж и выдачу подписки.
7. Пройдите `/admin/readiness`, настройте backup/offsite и мониторинг.
8. Включите продажи (`PURCHASES_ENABLED=1`) и боевой режим (`APP_ENV=prod`).

**Для тестового и боевого магазинов используйте отдельные окружения и БД.** Не переносите тестовые заказы в боевую систему.

## 4. Брендинг

Продукт остаётся ZeleBoba; каждый оператор настраивает свой визуал через `/admin/config` → секция «Брендинг». Код менять не нужно.

| Настройка | Формат | Где применяется |
|---|---|---|
| `SITE_NAME` | 1–60 символов | Название в шапке, подвале, title страниц |
| `BRAND_LOGO` | HTTPS URL картинки | Логотип в шапке кабинета (вместо буквы-логотипа) |
| `BRAND_FAVICON` | HTTPS URL картинки | Иконка вкладки браузера |
| `BRAND_COLOR` | `#RRGGBB` | Основной цвет: кнопки, ссылки, акценты |
| `BRAND_COLOR_ACCENT` | `#RRGGBB` | Второстепенные кнопки и подсветка |
| `BRAND_FOOTER_TEXT` | до 200 символов | Текст подвала |
| `BRAND_WELCOME_TEXT` | до 2000 символов | Приветствие бота (текст `/start`); пусто = стандартное |
| `BRAND_HELP_TEXT` | до 2000 символов | Справка бота (текст `/help`); пусто = стандартная |

Цвета применяются через CSS-переменные `--green` и `--lime`; валидация отклоняет не-`#RRGGBB` значения и не-HTTPS URL. Изменения подхватываются worker'ом автоматически, без перезапуска.

### 5.4. Безопасность платежей

- Сумма проверяется в копейках без float; несовпадение суммы отклоняет платёж.

- Платёж может оплатить только один заказ/пополнение.
- Повторное уведомление не дублирует зачисление.
- Создание платежа ограничено 23 часами от заказа (24-часовая гарантия idempotency провайдера). Позже — ручная сверка.

## 6. Кошелёк

### 6.1. Как работает

- Единый баланс в копейках (`users.balance_kopeks`).
- Пополнение создаёт `topups`-заказ; worker создаёт checkout у выбранного провайдера.
- После подтверждения платежа баланс зачисляется ровно один раз.
- Покупка с баланса списывает средства и создаёт подписку без повторной оплаты.
- История операций — в `/balance` (типы: пополнение, покупка, продление, конвертация триала, реферальная награда, подарок, промо-бонус, докупка трафика/устройств, возврат).

### 6.2. Умная корзина (автопокупка после пополнения)

Если клиент выбрал тариф, но на балансе не хватает средств:

1. Корзина сохраняется с меткой intent (в БД, таблица `carts`).
2. Клиент пополняет баланс любым провайдером.
3. После зачисления worker автоматически списывает баланс и завершает покупку (подписка, подарок, докупка трафика или устройств).
4. При неудаче корзина сохраняется с intent для повторной попытки; клиент получает уведомление.

Обычное пополнение без сохранённой корзины intent не ставит и ничего не покупает.

### 6.3. Ограничения

- Сумма пополнения: от 1 до 1 000 000 ₽.
- Ключ операции уникален внутри пользователя; повтор с другой суммой отклоняется.
- `has_made_first_topup` фиксирует первое пополнение (используется реферальной программой).

## 7. Промокоды

### 7.1. Типы

| Тип | Что даёт |
|---|---|
| `balance` | Деньги на баланс |
| `subscription_days` | Дни к активной подписке |
| `trial_subscription` | Триал (с привязкой к тарифу) |
| `discount` | Процентная скидка (1–100%) на срок в часах или до первой покупки |
| `balance_and_days` | Комбо: деньги + дни (+ трафик) |

### 7.2. Параметры

| Параметр | Описание |
|---|---|
| `code` | 3–50 символов A-Z, 0-9, `_`, `-` |
| `balance_bonus_kopeks` | Бонус в копейках (или процент для `discount`) |
| `subscription_days` | Дни (или часы действия для `discount`) |
| `traffic_gb` | Гигабайты к подписке |
| `max_uses` | Лимит использований (1–1 000 000) |
| `valid_from` / `valid_until` | Окно действия (unix) |
| `first_purchase_only` | Только для первой покупки |
| `plan_id` | Тариф для триала |

### 7.3. Правила

- Один пользователь — одно использование кода (уникальная пара user+code).
- Анти-стакинг: максимум 5 активаций за 24 часа.
- Скидки не стакаются: при активной скидке вторая отклоняется.
- Дни начисляются только при активной подписке; иначе код не сгорает (откат).
- Триал недоступен, если у пользователя уже есть подписка.
- Активация: веб `/settings` → «Промокод», бот `/promo <код>`.

## 8. Реферальная программа

### 8.1. Как работает

- Каждый пользователь получает код `REFERRAL_CODE` (8 символов) и ссылку `https://t.me/<бот>?start=ref_<код>`.
- При регистрации по ссылке реферер привязывается к пользователю (самореферал и привязка по email заблокированы).
- Награды начисляются с **пополнений** реферала.

### 8.2. Настройки

| Настройка | По умолчанию | Описание |
|---|---|---|
| `REFERRAL_PROGRAM_ENABLED` | 1 | Вкл/выкл |
| `REFERRAL_MINIMUM_TOPUP_KOPEKS` | 10000 | Минимум пополнения для «первого» |
| `REFERRAL_FIRST_TOPUP_BONUS_KOPEKS` | 10000 | Бонус рефералу за первое пополнение |
| `REFERRAL_INVITER_BONUS_KOPEKS` | 10000 | Фикс. бонус пригласившему |
| `REFERRAL_COMMISSION_PERCENT` | 25 | Комиссия с пополнений |
| `REFERRAL_FIRST_PAYMENT_COMMISSION_PERCENT` | — | Комиссия за первый платёж (если отличается) |
| `REFERRAL_RECURRING_COMMISSION_TIERS` | — | Ступени: `0:10,10:15,50:20` (по числу оплативших рефералов) |
| `REFERRAL_MAX_COMMISSION_PAYMENTS` | 0 | Лимит комиссионных платежей с одного реферала (0 = без лимита) |

### 8.3. Вывод средств

| Настройка | По умолчанию | Описание |
|---|---|---|
| `REFERRAL_WITHDRAWAL_ENABLED` | 0 | Вкл/выкл вывод |
| `REFERRAL_WITHDRAWAL_MIN_AMOUNT_KOPEKS` | 100000 | Минимум (1000 ₽) |
| `REFERRAL_WITHDRAWAL_COOLDOWN_DAYS` | 30 | Кулдаун между заявками |
| `REFERRAL_WITHDRAWAL_SUSPICIOUS_MIN_DEPOSIT_KOPEKS` | 50000 | Порог для риск-скоринга |
| `REFERRAL_WITHDRAWAL_SUSPICIOUS_MAX_DEPOSITS_PER_MONTH` | 10 | Порог для риск-скоринга |

- Выводятся только реферальные начисления (не собственный баланс).
- Каждая заявка получает риск-скоринг 0–100 (аномалии: много пополнений от одного реферала, крупные депозиты).
- Обработка: `/admin/withdrawals` → одобрить / отклонить / выплачено, с комментарием.
- Выплата выполняется оператором вручную (карта/кошелёк из реквизитов заявки).

## 9. Подарочные подписки

### 9.1. Формат кода

- Токен: 64 URL-safe символа (хранится в `guest_purchases.token`).
- Публичный код: `GIFT_<59 символов>` — оптимизирован под лимит Telegram start_param (64 символа).
- Полные токены и коды никогда не попадают в callback data, логи или сообщения об ошибках.

### 9.2. Покупка

- Включение: `CABINET_GIFT_ENABLED=1` в `/admin/config`.
- Тарифы для подарков: `show_in_gift` (по умолчанию 1).
- Покупка: веб `/gifts` (с баланса) или бот `/gift_buy <id тарифа>`.
- После покупки выдаётся код `GIFT_<59>` — отправьте его получателю.

### 9.3. Активация

| Способ | Как |
|---|---|
| Telegram deep-link | `https://t.me/<бот>?start=GIFT_<59>` — бот регистрирует/приветствует и активирует |
| Ручной ввод в боте | `/gift_claim <код>` |
| Ручной ввод в вебе | `/gifts` → «Активировать подарок» |
| Прямая ссылка | `https://<кабинет>/buy/gift/<64 токена>` |

### 9.4. Правила

- **Запрет самоактивации**: покупатель не может активировать свой подарок.
- **Право первого заявителя**: подарок закрепляется за первым активатором; попытки других отклоняются.
- **Идемпотентность**: повторный ввод кода тем же получателем возвращает успех без повторного начисления.
- **Бессрочность**: оплаченные подарки не сгорают.
- **«Мои подарки»**: покупатель видит коды и статусы; после активации код скрывается, показывается получатель и дата.
- При отключении `CABINET_GIFT_ENABLED` каталог скрывается, но ранее купленные подарки остаются активируемыми.

## 14. Автопродление

### 14.1. Настройки

| Настройка | По умолчанию | Описание |
|---|---|---|
| `AUTORENEW_ENABLED` | 0 | Вкл/выкл |
| `AUTORENEW_DAYS_BEFORE` | 3 | За сколько дней до истечения (1–14) |
| `AUTORENEW_MAX_FAILS` | 3 | Максимум неудач до отключения |

### 14.2. Как работает

1. Клиент включает автопродление на карточке подписки (веб или бот `/subs`).
2. За N дней до истечения scheduler ставит `subscription.renew`; worker создаёт renewal-заказ тем же тарифом и провайдером.
3. Клиент оплачивает по ссылке (как обычный заказ).
4. После оплаты срок продлевается от `max(now, expires_at)` + длительность; в Remnawave уходит PATCH с новым `expireAt`.
5. Неудачи: отменённый renewal → `renew_fail_count+1`, повтор через час; после лимита автопродление отключается.
6. Пауза продаж блокирует новые renewal-заказы.

Нативные рекурренты провайдеров не используются — продление идёт renewal-заказами, клиент каждый раз оплачивает по ссылке.

## 15. Синхронизация с Remnawave

- `remnawave:sync` (CLI), кнопка в админке, автораз в час.
- Для активных подписок сверяет `expireAt` / `trafficLimitBytes` / `hwidDeviceLimit` с панелью и чинит дрейф через PATCH.
- Если юзер пропал на панели — пересоздаёт (username детерминированный `zb_<subscription_id>`).
- Истёкшие подписки — `status=DISABLED` на панели.
- `--dry-run` показывает, что было бы исправлено, без изменений.
- Ошибки не роняют прогон — собираются в отчёт.

## 16. Бэкапы и восстановление

### 16.1. В админке (`/admin/backups`)

- «Создать бэкап» — полный SQL-дамп всех таблиц в `var/backups/backup-<timestamp>.sql`.
- «Восстановить» — перезаписывает текущую БД (с подтверждением).
- Имя файла строго `backup-YYYYMMDD-HHMMSS.sql`; path traversal отклоняется.

### 16.2. Скрипт (для сервера)

```sh
scripts/backup.sh /secure/backup-directory
```

Архив включает PostgreSQL custom dump, `master.key` и composer.lock. **Сам архив не зашифрован** — храните на зашифрованном носителе. Не храните единственный backup на сервере приложения.

### 16.3. Восстановление

1. Проверьте checksum архива, распакуйте в закрытый каталог.
2. Создайте пустую БД и роли; `pg_restore --exit-on-error` от имени владельца.
3. Поместите оригинальный `master.key` в volume `/app/var/master.key` (владелец www-data, права 0600).
4. Подключите изолированную app-реплику, примените новые миграции, назначьте runtime-права.
5. Проверьте `app:health`, `billing:audit`, расшифровку настроек, вход, несколько заказов.
6. **Не запускайте worker с реальными интеграциями на параллельной копии** — он может повторно отправить внешние операции.
7. После проверки переключите основной сервис.

### 17.3. Мониторинг

Контролируйте: недоступность `/health/ready`, ненулевой `billing:audit`, возраст paid-заказов, outbox dead > 0, просроченные heartbeat, ошибки внешних API. Готовой установки Prometheus/Alertmanager в репозитории нет.

### 17.4. Сбой оплаты или выдачи

- `pending` — платёж не подтверждён; браузерный redirect не меняет статус.
- `paid` — квитанция записана, выдача в durable outbox. Повторно оплачивать не нужно.
- `fulfilled` — панель ответила.
- 8 неудачных попыток → dead-letter. Исправьте причину и повторите из админки. Финансовые записи SQL вручную не редактировать.
- После 23 часов неопределённого создания платежа — ручная сверка; нельзя менять Idempotence-Key и создавать второе списание.
- Возвраты выполняются оператором в кабинете провайдера с отдельным отзывом доступа в панели. Автоматического возврата нет.

### 17.5. Обновление

Сделайте backup, соберите образ, примените миграции отдельным сервисом `migrate`, пересоздайте app/worker/scheduler/web. Старые SQL-файлы после применения не переписывать.

## 18. Безопасность

- Пароли Argon2id; серверные сессии; CSRF на всех POST.
- TOTP (SHA-1, 30 сек, окно ±1) + 8 recovery-кодов; админ-сессия 15 минут.
- Секреты зашифрованы (XChaCha20-Poly1305); ключ в `var/master.key` (0600), не в Git.
- Runtime-роль БД не может UPDATE/DELETE/TRUNCATE ledger, payment_receipts, audit_log.
- Rate limiting: вход (IP + email), мутации, webhook'и.
- Webhook'и провайдеров проверяют подписи; FreeKassa — IP whitelist.
- Порт web привязан к loopback; внешний HTTPS proxy перезаписывает Host и X-Forwarded-Proto.
- Не публикуйте внутренний HTTP endpoint напрямую.
