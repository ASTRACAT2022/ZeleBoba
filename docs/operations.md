# Эксплуатация и recovery

> Актуальная версия: **1.1**. Текущий production-статус — [STATUS.md](../STATUS.md).

## Команды

| Команда | Назначение |
|---|---|
| `db:migrate` | Применить новые SQL-миграции (роль `billing` — владелец схемы) |
| `db:grant-runtime` | Выдать приложению DML-права (устаревший путь при модели «billing-владелец») |
| `app:install email` | Создать первого владельца со скрытым вводом пароля |
| `worker:run` | Обрабатывать очередь и подхватывать настройки между заданиями |
| `billing:reconcile` | Пакетно поставить сверки в очередь, обработать локальные истечения, очистить временные токены |
| `remnawave:sync [--dry-run] [--limit=N]` | Сверить подписки с панелью: срок/трафик/устройства, пересоздать пропавших, отключить истёкших |
| `billing:audit` | Проверить квитанции, подписки и парные записи для оплаченных заказов |
| `app:health [worker\|scheduler]` | Проверить схему и heartbeat выбранного процесса |
| `app:doctor` | Диагностика условий запуска; exit 1 при невыполненных условиях |

`/health/live` отвечает без подключения к БД. `/health/ready` проверяет доступ к схеме; детальную версию схемы проверяет `app:health`. Readiness не должна использоваться как единственное доказательство работоспособности платежей.

Compose включает PHP-FPM, Nginx, PHP worker/scheduler и PostgreSQL 17. Отдельный Rails JSON API запускается только с профилем `rails` после задания `RAILS_SECRET_KEY_BASE`; Rails worker запускается отдельно с профилем `rails-worker`. Nginx отправляет `/rails/*` в Rails при запущенном API; рабочий Platega webhook `/webhooks/platega` и текущие HTML/Twig страницы остаются на PHP. Отдельный `/rails/webhooks/platega` доступен для изолированной проверки Rails и не должен указываться в рабочей конфигурации Platega до проверки cutover. Переключатель `RAILS_WRITE_GATEWAY_ENABLED=1` направляет шесть форм заказа, пополнения, покупки с баланса, продления подписки, покупки подарка и вывода реферальных средств из текущих PHP/Twig страниц в Rails; по умолчанию он выключен и включается только после проверки Rails на общей тестовой базе. `RAILS_INTERNAL_URL` задаёт внутренний адрес Rails API, по умолчанию `http://rails-api:3000`. Rails outbox worker в Compose выключен: его нельзя включать параллельно с PHP worker до сверки эксклюзивного claim и обработки новых Rails topics. Scheduler работает в одной логической очереди под lease; сверки читаются страницами по 100 записей. Все внешние HTTP-запросы имеют timeout, ограничение общей длительности и запрещённые redirects. Worker умеет завершать текущее задание по SIGTERM.

Супервизор контейнера `app` позволяет независимо отключить фоновые PHP-роли, сохранив PHP-FPM и текущие страницы. Переменные `RUN_PHP_OUTBOX_WORKER`, `RUN_PHP_SCHEDULER` и `RUN_PHP_TELEGRAM_POLL` по умолчанию равны `1`; значение `0` выключает только соответствующую роль, а healthcheck перестаёт ждать её heartbeat. Это переключатели для контролируемой миграции, сами по себе они не доказывают безопасность cutover. Перед остановкой PHP worker нужно остановить его процесс и дождаться отсутствия активных claims; Rails worker включать только после database-backed проверки совместимости и единственного владельца очереди. Telegram long-poll и webhook нельзя запускать одновременно для одного bot token.

Rails-периодические задачи (отправка очереди писем и очистка истёкших сессий/временных токенов) запускаются только при `RAILS_SCHEDULER_ENABLED=1`. Флаг сам по себе не отключает PHP scheduler. Перед включением остановите PHP scheduler (`RUN_PHP_SCHEDULER=0`) и дождитесь завершения активного `billing:reconcile`; Rails и PHP дополнительно используют общий lease `reconcile`, чтобы их задачи не шли одновременно. После подтверждения, что PHP scheduler больше не работает, включите `RAILS_SCHEDULER_ENABLED=1` у Rails worker. Команда `zeleboba:flush_mail` использует тот же lease и флаг. Не запускайте отдельный mail flusher в период перехода.

## OpenTelemetry

Трассировка включается без изменения кода. Передайте всем контейнерам приложения,
worker и scheduler одинаковые переменные окружения:

```text
OTEL_PHP_AUTOLOAD_ENABLED=true
OTEL_SERVICE_NAME=zeleboba-billing
OTEL_TRACES_EXPORTER=otlp
OTEL_METRICS_EXPORTER=none
OTEL_LOGS_EXPORTER=none
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
OTEL_EXPORTER_OTLP_PROTOCOL=http/protobuf
OTEL_TRACES_SAMPLER=parentbased_traceidratio
OTEL_TRACES_SAMPLER_ARG=0.1
```

Приложение экспортирует span'ы `billing.http.request` и
`billing.outbox.process`. В атрибуты не попадают email, платежные ID, токены,
URL подписок и содержимое очереди. Если collector недоступен или переменные не
заданы, обработка платежей и очереди продолжает работать без телеметрии.

## Права и сеть

Приложение работает под ролью `billing`, которая **владеет схемой `public` и всеми объектами** (таблицы, sequence, дефолты) — решение принято оператором (2026-09-21), чтобы `db:migrate` в контейнере накатывал SQL-миграции штатно без отдельной роли. Это даёт приложению и право DDL; для бэкапов/администрирования сохранена роль `billing_owner` (суперпользователь). Если требуется более строгая модель «runtime без DDL» — верните владельца схемы роли `billing_owner`, а миграции накатывайте под ней отдельно (не через `db:migrate` в контейнере).

SQL инициализации Docker выполняется только при первом создании пустого volume. Существующую PostgreSQL нельзя перевести на новую модель простым изменением `.env`: создайте runtime-роль через владельца, примените миграции, выполните `db:grant-runtime`, смените подключение приложения, затем проверьте права. Не удаляйте volume ради обновления.

Порт web привязан к loopback. Внешний HTTPS proxy должен перезаписывать Host и X-Forwarded-Proto; пример есть в infra. Не публикуйте внутренний HTTP endpoint напрямую: при такой публикации trust boundary для forwarded headers нарушится. Cookie Secure в боевом режиме включается независимо от forwarded headers. Внутренний Nginx принимает X-Real-IP только от host/bridge-диапазонов. Внешний proxy обязан перезаписывать этот заголовок адресом клиента. Уточните доверенные диапазоны под вашу сеть; иначе лимиты могут агрегироваться по адресу прокси.

Образы PHP, PostgreSQL, Nginx и Ruby закреплены digest. Rails runtime использует Ruby 4.0.5 и `rails_backend/Gemfile.lock`; перед запуском Compose задайте отдельный случайный `RAILS_SECRET_KEY_BASE` вместе с существующими секретами. Для обновления безопасности нужно целенаправленно обновить image digest, собрать образ и повторить тесты. Composer и Bundler lock-файлы закреплены отдельно. CI включает тесты, composer audit и Docker build; удалённый CI запускается после публикации репозитория.

## Резервирование

```sh
scripts/backup.sh /secure/backup-directory
```

Архив включает PostgreSQL custom dump, 32-байтовый `master.key`, обнаруженные lock-файлы (`composer.lock` и/или `rails_backend/Gemfile.lock`) и краткую памятку. По умолчанию скрипт сохраняет PHP Compose значения: сервисы `db`/`app`, БД `billing`, роль `billing_owner`, ключ `/app/var/master.key`. Для Rails deployment задайте параметры, соответствующие его Compose и runtime-конфигурации:

```sh
BACKUP_DB_SERVICE=db \
BACKUP_APP_SERVICE=rails-api \
BACKUP_DB_NAME=billing \
BACKUP_DB_USER=billing_owner \
BACKUP_MASTER_KEY_PATH=/app/var/master.key \
  scripts/backup.sh /secure/backup-directory
```

Переменные `BACKUP_DB_SERVICE`, `BACKUP_APP_SERVICE`, `BACKUP_DB_NAME`, `BACKUP_DB_USER` и `BACKUP_MASTER_KEY_PATH` переопределяют значения по умолчанию; путь ключа должен быть абсолютным путём внутри контейнера приложения. Сервисные имена, имя базы и роль должны соответствовать ограниченному формату PostgreSQL/Compose. Скрипт проверяет наличие lock-файла, Docker, непустой dump, 32-байтовый ключ и не перезаписывает архивы. Имя архива содержит UTC-время и случайный суффикс; checksum записывается рядом.

Каталог и архив имеют закрытые права; **сам архив не зашифрован** и содержит ключ шифрования. Храните его на зашифрованном носителе или зашифруйте backup-агентом перед offsite-передачей. Не храните единственный backup на сервере приложения. Частоту и retention задаёт ваша инфраструктура; скрипт сам ничего не планирует и не удаляет старые архивы.

Ключ не меняется автоматически; пара dump + исходный master.key обязательна. Если планируется ротация ключа, нужна отдельная процедура с переупаковкой всех зашифрованных значений, включая очередь и TOTP.

## Восстановление

Восстановление выполняется оператором. Не добавляйте восстановление поверх текущей БД в Rails web/API: это разрушительная операция с уровнем доступа владельца БД. Сначала восстановите архив в **новую, изолированную БД**, не поверх работающей:

1. Проверьте checksum архива и распакуйте его в закрытый каталог.
2. Создайте пустую БД и роли владельца/runtime. Используйте имя назначения, отличающееся от рабочей БД. Выполните `pg_restore --exit-on-error` custom dump от имени владельца. Имена ролей должны соответствовать архиву; для другой среды используйте `--no-owner --no-acl` и назначьте права заново. Не указывайте production connection string как цель восстановления.
3. Поместите оригинальный `master.key` в volume `/app/var/master.key`; владелец www-data, права 0600.
4. Подключите изолированную app-реплику к восстановленной БД. Для Rails задайте `DATABASE_NAME`/`DATABASE_URL` на новую БД и `ZELEBOBA_MASTER_KEY_FILE` (либо смонтируйте исходный ключ в стандартный путь). Примените необходимые новые миграции владельцем и назначьте runtime-права. Сверьте версию приложения по соответствующему lock-файлу из архива.
5. Выполните `app:health`, `billing:audit`, проверьте расшифровку настроек, вход и несколько заказов. **Не запускайте worker с реальными интеграциями на параллельной копии:** это может повторно отправить внешние операции.
6. После проверки и остановки старой записи переключите основной сервис на восстановленную БД.

После портирования приложения инструмент совместим с PHP и Rails через явные overrides, но это не заменяет restore rehearsal. Backup/restore на целевой Rails-конфигурации должен быть проверен на синтетических данных до cutover. RPO/RTO и offsite-передача зависят от вашей инфраструктуры и не измерялись.

## Сбой оплаты или выдачи

- `pending` — платёж ещё не подтверждён; браузерный redirect не меняет статус.
- `paid` — квитанция записана, выдача поставлена в durable outbox. Повторно оплачивать не нужно.
- `fulfilled` — панель ответила, результат сохранён локально.
- Восемь неудачных попыток переводят задание в dead-letter. Исправьте причину и повторите из админки. Финансовые записи SQL вручную не редактировать.
- Периодический опрос восстанавливает пропущенные уведомления известных платежей. После 23 часов неопределённого создания платежа требуется ручная сверка: нельзя менять Idempotence-Key и создавать второе списание.
- Срок подписки начинается при фиксации оплаты и не увеличивается от повторных вызовов. Если выдача долго не работала, оператор должен согласовать компенсацию срока либо возврат; автоматическая компенсация не реализована.
- Возвраты сейчас выполняются оператором в кабинете Platega с отдельным отзывом доступа в панели. Автоматического возврата/учёта возвратов в версии 0.3 нет. До запуска утвердите эту процедуру и ответственного; интерфейс не должен обещать клиенту автоматический возврат.
- Platega: автовывод/вывод средств настраивается в кабинете app.platega.io.

## Мониторинг

Контролируйте: недоступность `/health/ready`, ненулевой `billing:audit`, возраст paid-заказов, outbox dead > 0, просроченные heartbeat, ошибки внешних API. Docker restart policy не перезапускает контейнер только потому, что он unhealthy: монитор должен оповещать оператора, а оркестратор — реагировать на liveness по своей политике. Готовой установки Prometheus/Alertmanager и внешнего канала оповещений в репозитории нет.

## Обновление

Сделайте backup, соберите образ, примените миграции отдельным сервисом `migrate`, затем пересоздайте app/worker/scheduler/web. Старые SQL-файлы после применения не переписывать. Для версии 0.1 с реальными заказами требуется отдельная проверка новых snapshots: значения `provision_driver`, `provider_account` и `squad_uuid` нужно перенести из старой конфигурации до включения worker. Автоматически угадывать панель и магазин старых заказов небезопасно.
