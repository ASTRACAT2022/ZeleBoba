# Эксплуатация версии 0.2

## Команды

| Команда | Назначение |
|---|---|
| `db:migrate` | Применить новые SQL-миграции; запускать ролью владельца |
| `db:grant-runtime` | Выдать runtime-права без DDL и изменения ledger/audit |
| `app:install email` | Создать первого владельца со скрытым вводом пароля |
| `worker:run` | Обрабатывать очередь и подхватывать настройки между заданиями |
| `billing:reconcile` | Пакетно поставить сверки в очередь, обработать локальные истечения, очистить временные токены |
| `billing:audit` | Проверить квитанции, подписки и парные записи для оплаченных заказов |
| `app:health [worker\|scheduler]` | Проверить схему и heartbeat выбранного процесса |
| `app:doctor` | Диагностика условий запуска; exit 1 при невыполненных условиях |

`/health/live` отвечает без подключения к БД. `/health/ready` проверяет доступ к схеме; детальную версию схемы проверяет `app:health`. Readiness не должна использоваться как единственное доказательство работоспособности платежей.

Compose включает PHP-FPM, Nginx, worker, scheduler и PostgreSQL 17. Scheduler работает в одной логической очереди под lease; сверки читаются страницами по 100 записей. Все внешние HTTP-запросы имеют timeout, ограничение общей длительности и запрещённые redirects. Worker умеет завершать текущее задание по SIGTERM.

## Права и сеть

Runtime-роль `billing` получает SELECT/INSERT/UPDATE/DELETE только в нужной схеме, с дополнительным запретом UPDATE/DELETE/TRUNCATE ledger, payment_receipts, audit_log и записи migrations. Роль `billing_owner` используется только при миграции и backup. Пароль владельца не передаётся app/worker/scheduler.

SQL инициализации Docker выполняется только при первом создании пустого volume. Существующую PostgreSQL нельзя перевести на новую модель простым изменением `.env`: создайте runtime-роль через владельца, примените миграции, выполните `db:grant-runtime`, смените подключение приложения, затем проверьте права. Не удаляйте volume ради обновления.

Порт web привязан к loopback. Внешний HTTPS proxy должен перезаписывать Host и X-Forwarded-Proto; пример есть в infra. Не публикуйте внутренний HTTP endpoint напрямую: при такой публикации trust boundary для forwarded headers нарушится. Cookie Secure в боевом режиме включается независимо от forwarded headers. Внутренний Nginx принимает X-Real-IP только от host/bridge-диапазонов. Внешний proxy обязан перезаписывать этот заголовок адресом клиента. Уточните доверенные диапазоны под вашу сеть; иначе лимиты могут агрегироваться по адресу прокси.

Образы PHP, PostgreSQL и Nginx закреплены digest. Для обновления безопасности нужно целенаправленно обновить digest, собрать образ и повторить тесты. Composer lock закреплён отдельно. CI включает тесты, composer audit и Docker build; удалённый CI запускается после публикации репозитория.

## Резервирование

```sh
scripts/backup.sh /secure/backup-directory
```

Архив включает PostgreSQL custom dump, `master.key` и composer.lock. Каталог и архив имеют закрытые права; **сам архив не зашифрован**. Храните его на зашифрованном носителе или зашифруйте вашим backup-агентом перед offsite-передачей. Не храните единственный backup на сервере приложения. Частоту и retention задаёт ваша инфраструктура; скрипт сам ничего не планирует и не удаляет старые архивы.

Ключ не меняется автоматически; пара dump + исходный master.key обязательна. Если планируется ротация ключа, нужна отдельная процедура с переупаковкой всех зашифрованных значений, включая очередь и TOTP.

## Восстановление

Сначала восстановите в **новую БД**, не поверх работающей:

1. Проверьте checksum архива и распакуйте его в закрытый каталог.
2. Создайте пустую БД и роли владельца/runtime. Выполните `pg_restore --exit-on-error` custom dump от имени владельца. Имена ролей должны соответствовать архиву; для другой среды используйте `--no-owner --no-acl` и назначьте права заново.
3. Поместите оригинальный `master.key` в volume `/app/var/master.key`; владелец www-data, права 0600.
4. Подключите изолированную app-реплику к восстановленной БД. Примените необходимые новые миграции владельцем и назначьте runtime-права.
5. Выполните `app:health`, `billing:audit`, проверьте расшифровку настроек, вход и несколько заказов. **Не запускайте worker с реальными интеграциями на параллельной копии:** это может повторно отправить внешние операции.
6. После проверки и остановки старой записи переключите основной сервис на восстановленную БД.

В этой разработке backup/restore проверен на синтетических данных PostgreSQL 17. RPO/RTO и offsite-передача зависят от вашей инфраструктуры и не измерялись.

## Сбой оплаты или выдачи

- `pending` — платёж ещё не подтверждён; браузерный redirect не меняет статус.
- `paid` — квитанция записана, выдача поставлена в durable outbox. Повторно оплачивать не нужно.
- `fulfilled` — панель ответила, результат сохранён локально.
- Восемь неудачных попыток переводят задание в dead-letter. Исправьте причину и повторите из админки. Финансовые записи SQL вручную не редактировать.
- Периодический опрос восстанавливает пропущенные уведомления известных платежей. После 23 часов неопределённого создания платежа требуется ручная сверка: нельзя менять Idempotence-Key и создавать второе списание.
- Срок подписки начинается при фиксации оплаты и не увеличивается от повторных вызовов. Если выдача долго не работала, оператор должен согласовать компенсацию срока либо возврат; автоматическая компенсация не реализована.
- Возвраты сейчас выполняются оператором в кабинете FreeKassa / ЮKassa с отдельным отзывом доступа в панели. Автоматического возврата/учёта возвратов в версии 0.3 нет. До запуска утвердите эту процедуру и ответственного; интерфейс не должен обещать клиенту автоматический возврат.
- FreeKassa: автовывод на FKWallet настраивается в merchant.freekassa.net → Настройки → Вывод. В FKWallet обмен RUB → USDT (не USD) и вывод на ваш адрес. Верификация не нужна. Лимиты вывода: СБП от 6000 ₽, карты РФ от 2000 ₽ (массовые СБП от 150 ₽ — по договорённости).

## Мониторинг

Контролируйте: недоступность `/health/ready`, ненулевой `billing:audit`, возраст paid-заказов, outbox dead > 0, просроченные heartbeat, ошибки внешних API. Docker restart policy не перезапускает контейнер только потому, что он unhealthy: монитор должен оповещать оператора, а оркестратор — реагировать на liveness по своей политике. Готовой установки Prometheus/Alertmanager и внешнего канала оповещений в репозитории нет.

## Обновление

Сделайте backup, соберите образ, примените миграции отдельным сервисом `migrate`, затем пересоздайте app/worker/scheduler/web. Старые SQL-файлы после применения не переписывать. Для версии 0.1 с реальными заказами требуется отдельная проверка новых snapshots: значения `provision_driver`, `provider_account` и `squad_uuid` нужно перенести из старой конфигурации до включения worker. Автоматически угадывать панель и магазин старых заказов небезопасно.
