# Результаты проверки · 21.09.2026 · версия 1.1

## Автоматические проверки

**43 теста, 159 утверждений, без ошибок и пропусков.** Набор прошёл:

- на PHP 8.4.25 хоста с PostgreSQL 16;
- внутри собранного production PHP 8.4.25 образа с PostgreSQL 17 в Docker.

Проверены идемпотентность заказа/платежа, snapshots цены и чека, rollback, неправильная сумма/валюта/провайдер, чужой заказ, повторная квитанция, очередь и lease, dead-letter, шифрование настроек/очереди, конфликт версии настроек, Telegram challenge/magic flow, одноразовость и истечение, заблокированный аккаунт, TOTP/recovery и повторный код, admin MFA, CSRF, HTML escaping, новые admin-страницы.

Конкурентные сценарии PostgreSQL: 6 одинаковых checkout-запросов → 1 заказ; 6 подтверждений → 1 подписка и 1 квитанция; 6 workers корректно разбирают очередь; 6 потреблений magic link → 1 сессия.

`composer validate --strict`, PHP syntax checks и `composer audit` успешны. На момент проверки известных advisories установленных PHP-пакетов не найдено. Это не сканирование всех OS-пакетов контейнера.

## Docker и база

- Production Dockerfile успешно собран с реальными расширениями и `composer install --no-dev`.
- Отдельный Compose-проект `zeleboba-verify`: PostgreSQL 17, PHP-FPM, Nginx, worker, scheduler; web был доступен только на loopback:8082.
- Начальная БД создана с отдельными billing_owner и billing. Миграции и выдача runtime-прав успешны.
- Runtime фактически отклоняет UPDATE ledger, DELETE audit и CREATE TABLE с SQLSTATE 42501.
- Пароль DATABASE_MIGRATION_PASSWORD отсутствует в окружении app.
- Сервисы работают, app/db/worker/scheduler healthy; отдельные heartbeat-проверки успешны.
- `nginx -t` успешен; конфигурация перезагружена.
- `billing:audit`: 0 нарушений на сквозном демозаказе.

## Browser QA

На отдельном синтетическом QA-аккаунте через реальный HTTP/Nginx/PHP-FPM:

- Вход по паролю с текущим TOTP и переход в админку.
- Сохранение названия сервиса через форму admin/config, подтверждение результата и обновлённый бренд.
- Визуальная проверка desktop и 390×844. Горизонтального переполнения на проверенной mobile-странице нет, поля перестраиваются в одну колонку.
- Выбор тарифа → создание заказа → демооплата без денег → queued paid → fulfilled фоновой очередью.
- После mobile-проверки добавлена кнопка выхода в настройках профиля: она доступна независимо от скрытого мобильного sidebar footer.

## Backup / restore

`scripts/backup.sh` создал архив с custom dump и master.key. Архив восстановлен в отдельную billing_restore. Проверено равенство количества заказов, расшифровка TOTP восстановленным ключом и сохранение ограничений runtime-роли. Исходная тестовая БД не перезаписывалась.

Это функциональная проверка восстановления, не измерение RPO/RTO или offsite-доставки.

## Что не подтверждено

- Публичный HTTPS-домен, сертификат и reverse proxy целевого сервера.
- Реальный Telegram-бот и доставка webhook через интернет.
- Магазин ЮKassa: live/sandbox, чек с налоговыми параметрами конкретного продавца и реальные уведомления.
- Магазин Platega: live-контракт подтверждён в проде (см. `STATUS.md`): amount whole RUB, net-of-commission settlement, `GET /transaction/{id}` verify, webhook `{payment_id,status,metadata,order_id}`.
- Версия Remnawave пользователя, фактическое создание доступа и работа выбранного squad.
- Нагрузочные SLO, внешние оповещения и offsite-backup инфраструктуры пользователя.

Ключи интеграций и адрес целевого сервера не были предоставлены. Боевые покупки не включались. Автоматические возвраты, продление/автопродление и кошелёк в эту версию не входят; границы описаны в parity.md и operations.md.
